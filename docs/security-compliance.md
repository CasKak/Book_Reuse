## 1. 数据分级

按《数据安全法》第 21 条的数据分类分级要求，结合本项目实际：

| 级别 | 名称 | 数据示例 | 存储要求 | 访问控制 |
|---|---|---|---|---|
| L1 | 公开数据 | 图书标题、ISBN、作者、出版社、公开的图书列表 | 普通存储 | 任何人可读 |
| L2 | 内部数据 | 库存数量、定价系数、运营统计 | 普通存储 + 仅登录可见 | 按角色 |
| L3 | 个人信息 | 姓名、手机号、邮箱、学校、专业、年级、收货地址、订单记录 | 加密传输 + 最小采集 | 仅本人 + 必要运营角色 |
| L4 | **敏感个人信息** | 学生证照片、身份证号、人脸/生物特征、支付信息、精确定位 | **单独同意 + 加密存储 + 严格留存期限 + 访问审计** | 仅本人 + 极少数授权角色 |

> ⚠️ **人脸信息属生物识别信息**，是敏感个人信息中的高风险项。商业计划书 3.2 节提到
> 「摄像头采集图像」，若用于**识别到具体个人**，需单独同意 + 影响评估（PIPIA）。
> **建议**：品相识别只拍书、不拍人，从设计上规避。

### 1.1 敏感个人信息的处理要求（PIPIA）

《个人信息保护法》第 55 条要求处理敏感个人信息前进行**个人信息保护影响评估**并留存记录至少 3 年。
本项目需做评估的场景：

| 场景 | 是否需 PIPIA | 处理方式 |
|---|---|---|
| 学生证照片上传（身份认证） | **需要** | 加密存储、限定留存 6 个月、审核通过后可选删除原图 |
| 智能柜摄像头采集图书图像 | 否（不涉及个人） | 画面中避免出现人 |
| 收货地址（校内宿舍） | 需评估 | 精度限制到楼栋，不要求精确门牌 |
| 手机号 | 需评估 | 加密存储，展示时脱敏（138****8888） |

## 2. 加密与传输

| 环节 | 措施 |
|---|---|
| 传输层 | 全站 HTTPS（TLS 1.2+），HSTS 开启，禁止 HTTP 回退 |
| 数据库 | Supabase 托管 PG 默认静态加密；自托管需在云盘层面加密 |
| 敏感字段 | 手机号、地址等建议**应用层加密**（pgcrypto 或 Edge Function 加密后入库） |
| 密钥管理 | `service_role` 只存 Edge Function Secrets / 部署平台环境变量，**永不进代码库** |
| 文件存储 | Storage 桶设为 **private**，通过**签名 URL**（有效期 ≤1 小时）临时授权访问 |
| 备份加密 | 数据库备份文件加密后异地存放 |

**反例（禁止）**：

```ts
// ❌ 绝对禁止：密钥硬编码
const supabase = createClient(
  'https://<project-ref>.supabase.co',
  '<anon-key>'
)

// ✅ 正确：从环境变量读取，且启动时校验存在性
const env = readEnv()   // 内部用 Zod 校验，缺失即抛错
const supabase = createClient(env.VITE_SUPABASE_URL, env.VITE_SUPABASE_ANON_KEY)
```

## 3. 隐私政策与用户协议要点

上线前必须提供两份法律文本，并**在注册页以勾选方式取得同意**（不得默认勾选）。

### 3.1 隐私政策必含条款（PIPL 第 17 条）

1. 处理者身份与联系方式
2. 收集的个人信息**种类、用途、方式**
3. **保存期限**（每类数据单独说明）
4. 对外提供/共享情况（如物流、支付机构）
5. 用户权利及行使方式（查阅、复制、更正、删除、注销、可携带）
6. 未成年人条款：**不满 14 周岁需监护人同意**；高校场景中未成年用户虽少但不得遗漏
7. 投诉渠道与响应时限
8. 政策变更通知方式

### 3.2 用户协议必含条款

- 账号规则与实名要求
- **版权条款（关键）**：平台仅流转合法取得的正版实体图书；禁止翻印、复印、未授权讲义与考研资料
- 交易规则、押金与损耗条款（引自计划书 4.2.2：押金 = 售价 80%，逾期 0.5 元/日）
- 免责与责任限制
- 争议解决与适用法律

> ⚠️ **版权合规是计划书 9.1 节明确要求**，也是本项目最大法律风险。
> 系统层面必须落实三层风控（见第 6 节）。

## 4. Supabase 生产环境加固清单

> 阶段 9 部署前逐项打勾；未打勾项不得上线。

### 4.1 数据库与 RLS

- [ ] 每张表都有明确的 `SELECT / INSERT / UPDATE / DELETE` 策略，**不依赖「无策略即拒绝」的默认行为去猜**

- [ ] 敏感字段（手机号、地址）通过**视图 + 列级权限**隔离，不直接暴露基表

### 4.2 认证与账号

- [ ] 关闭不必要的注册方式（如匿名登录），只保留邮箱/密码
- [ ] 开启邮箱验证
- [ ] 配置密码强度策略与登录失败限流
- [ ] **管理员账号强制开启 MFA（TOTP）**
- [ ] 定期清理僵尸账号与过期会话

### 4.3 网络与接口

- [ ] 生产数据库**禁止公网直连**，只允许通过 Supabase API 与白名单 IP
- [ ] Storage 桶全部 private，仅签名 URL 可读
- [ ] Edge Functions 校验调用方 JWT 与角色，不信任前端传参
- [ ] 开启速率限制（防刷单、防爬虫、防暴力破解）

- [ ] 建立密钥轮换计划（建议 90 天）

### 4.5 审计与监控

- [ ] 关键表启用审计触发器（`audit_logs`）
- [ ] 后台管理员的每次写操作留痕（谁、何时、改了什么、改前改后）

- [ ] 数据导出行为告警

## 5. 多环境与数据库迁移流程

### 5.1 环境隔离要求

| 项 | 本地 | 预发布 | 生产 |
|---|---|---|---|
| Supabase 项目 | 本地 Docker 或独立云项目 | 独立云项目 | 独立云项目 |
| 数据 | 种子数据（示例） | 脱敏测试数据 | 真实数据 |
| RLS | 开启 | 开启 | 开启 |
| 备份 | 不需要 | 每日 | 每日 + PITR |

**严禁**：本地开发直连生产数据库。**严禁**：用生产数据做测试。

### 5.2 迁移流程（强制）

```
① 本地改结构  →  写迁移文件 supabase/migrations/<timestamp>_<name>.sql
② 本地验证    →  supabase db reset 全量重建 + 跑 RLS 测试
③ 提交 PR     →  迁移文件随代码一起评审
④ 合入 main   →  CI 校验迁移可执行
⑤ 部署预发布  →  supabase db push（预发布）
⑥ 验收通过    →  supabase db push（生产）
```

> 🚫 **红线：严禁在生产环境用 Supabase 仪表盘直接改表结构。**
> 原因：仪表盘改动不会生成迁移文件，导致「生产库与代码库不一致」，
> 下一次部署会覆盖或报错，且无法回滚、无法审计。

### 5.3 迁移文件规范

- 命名：`YYYYMMDDHHMMSS_动词_对象.sql`，如 `20260115103000_create_listings_table.sql`
- 每个迁移**只做一件事**，便于定位与回滚
- 必须包含**回滚说明**注释（Supabase CLI 不支持自动回滚，需人工写 down 脚本）
- 破坏性变更（删列/改类型）必须**分两次发布**：先加新列并双写，确认无误后再删旧列

## 6. 版权技术风控（计划书 9.1 节要求）

计划书明确要求三层风控，系统实现如下：

| 层级 | 风控点 | 实现方式 |
|---|---|---|
| 第一层 | ISBN 权威库比对 | 发布时校验 ISBN 格式与有效性；无 ISBN / 信息不符 → 自动拒绝收录 |
| 第二层 | 人工二次审核 | AI 置信度低或疑似资料类物品 → 进入人工待审队列；发现违规即下架 + 用户黑名单 |
| 第三层 | 系统对接合规 | 涉及教务系统对接时，须取得学校正式授权并完成数据安全评估，遵循最小必要原则 |

**数据库支撑**：`audit_logs` 记录下架原因与操作人；`profiles` 增加 `blacklist_reason` 字段。

## 7. 可观测性方案

### 7.1 日志

| 类型 | 内容 | 留存 |
|---|---|---|
| 应用日志 | 请求、错误、耗时 | 30 天 |
| 审计日志 | 后台写操作、权限变更 | **≥6 个月**（等保要求） |
| 安全日志 | 登录失败、越权尝试、限流触发 | ≥6 个月 |

**日志脱敏**：手机号、地址、邮箱在日志中必须脱敏，禁止打印完整 JWT 与密码。

### 7.2 指标（RED 方法）

对每个关键接口采集：

| 指标 | 含义 | 告警阈值（建议） |
|---|---|---|
| **R**ate | 请求速率 | 突增/突降 50% 告警 |
| **E**rrors | 错误率 | >1% 告警，>5% 严重 |
| **D**uration | 响应时长 | P95 > 500ms 告警 |

业务指标另设：下单成功率、支付成功率（模拟阶段为「模拟支付」成功率）、库存周转天数。

### 7.3 告警渠道

- 严重（数据库不可用、错误率 >5%）：短信 + 电话
- 一般（错误率 >1%、磁盘 >80%）：企业微信/钉钉机器人
- 提示（部署完成、备份完成）：群消息

### 7.4 备份与恢复

| 项 | 策略 |
|---|---|
| 自动备份 | Supabase 每日自动备份 |
| **PITR（时间点恢复）** | 生产环境**必须开启**（需付费计划），支持恢复到任意时间点 |
| 备份验证 | **每月做一次恢复演练**，把备份恢复到临时实例并验证数据完整 |
| 异地存放 | 备份文件加密后同步到对象存储（不同区域） |
| RPO / RTO | 目标 RPO ≤ 5 分钟，RTO ≤ 2 小时 |

> ⚠️ **没有验证过的备份等于没有备份**。恢复演练必须记录在案。

## 8. 等保 2.0 适配要点

> 说明：等保 2.0（GB/T 22239-2019）的**定级备案**主要面向网络运营者。
> 学生创业团队初期通常不强制，但以下情形会触发要求：
> ① 学校/政府项目采购要求提供等保备案证明；② 系统被认定为二级及以上；
> ③ 处理大量个人信息达到监管阈值。**建议在接入学校官方合作前完成定级评估。**

| 等保要求域 | 本项目对应措施 |
|---|---|
| 安全物理环境 | 使用合规云服务商（阿里云/腾讯云）机房 |
| 安全通信网络 | HTTPS/TLS、网络分区、数据库不公网暴露 |
| 安全区域边界 | 防火墙、WAF、CORS 白名单、速率限制 |
| 安全计算环境 | 身份鉴别（MFA）、访问控制（RLS）、入侵防范、恶意代码防范、数据完整性/保密性、数据备份恢复、剩余信息保护、个人信息保护 |
| 安全管理中心 | 集中日志、集中管控、审计 |
| 安全管理制度 | 建立制度文档：安全策略、管理制度、人员安全、系统建设、系统运维 |
| 安全管理人员 | 背景审查、离职流程、安全意识培训 |
| 安全建设管理 | 定级备案、安全设计、产品采购、测试验收、上线检查 |
| 安全运维管理 | 环境管理、资产管理、介质管理、漏洞管理、变更管理、应急预案 |

**最低限度落地清单（现阶段）**：

1. 建立《安全管理制度》文档（可与隐私政策合并起步）
2. 账号最小权限 + MFA
3. 全量审计日志留存 ≥6 个月
4. 定期漏洞扫描（`npm audit` + 依赖更新）
5. 制定《数据安全事件应急预案》（含上报流程与时限）
